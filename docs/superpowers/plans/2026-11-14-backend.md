# Zuma Go Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Implement a verified local Zuma backend for Godot with SQLite, reports, and Qwen3 8B through Ollama.

**Architecture:** One Go process serves HTTP, calculates measures, stores data, and produces reports. Ollama is called through a separate time-limited request. Go builds the explanation from allowed facts selected by the model.

**Tech Stack:** Go, net/http, database/sql, modernc.org/sqlite, html/template, Ollama HTTP API.

**Spec:** `docs/superpowers/specs/2026-11-14-backend-design.md` (approved).

## Global Constraints

- Server in `server/`, a separate Go module; the game client is not implemented.
- Defaults: `127.0.0.1:8080`, `./data/zuma.db`, `http://127.0.0.1:11434`, `qwen3:8b`.
- Local HTTP interface only, without CORS or user authentication.
- Protocol `reaction-memory-v1`, calculation version `v1`.
- Mandatory self-report, reaction, and memory; saved in one transaction.
- `source`: `observed` or `synthetic`; sources are compared separately.
- Request body at most 256 KiB; limit=20, maximum 100; offset>=0.
- Generation timeout 120 seconds; at most one concurrent generation.
- SQLite/model/builds stay out of Git; the workflow works offline after installation.
- Watches are excluded; no diagnoses or universal health score.

## Review Focus

- Zero values on mandatory scales are valid; missing/null fields are rejected (tasks 1, 4).
- Retrying with reordered keys does not create a new record; concurrent retries are also safe (task 2).
- A backfilled session changes the baseline and makes the old explanation stale (tasks 2, 3).
- Generation cancellation/timeout releases the slot and preserves an already-ready explanation (task 3).
- HTML escapes profile names; model failures do not disrupt offline use (tasks 4, 6).
