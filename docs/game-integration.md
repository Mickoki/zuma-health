# Протокол будущих заданий реакции и памяти

Четыре подключённые мини-игры используют отдельный протокол и API: [minigames.md](../server/docs/minigames.md). Этот документ относится только к будущим сценам реакции и памяти.

Пока игровые сцены не находятся в этом проекте, кнопка запуска заданий скрыта.
Приложение запускает игры последовательно, когда обе сцены доступны;
до подключения согласуйте механику `reaction-memory-v1` с backend-командой.
Не присваивайте этот протокол игре с иной механикой только ради сохранения:
сервер использует версию для выбора сопоставимых предыдущих результатов.

## Подключение сцен

Добавьте сцены `res://scenes/games/reaction.tscn` и
`res://scenes/games/memory.tscn`. Корень каждой сцены должен наследовать `Control`
и объявлять сигналы `completed(result: Dictionary)` и `cancelled`. После успешного
завершения задания отправьте `completed.emit(result)` с результатом в формате
ниже; при отмене — `cancelled.emit()`. Сцены размещаются внутри экрана приложения,
поэтому не должны самостоятельно переключать основную сцену или отправлять сессию.
После завершения сцена удаляется приложением. Реакция запускается первой, память —
второй. Во время задания переключение раздела и профиля недоступно; кнопка
«Отменить проверку» прерывает текущую проверку и возвращает к опросу.

Сцена размещается внутри прокручиваемого экрана, а не занимает всё окно. Корень
получает доступную ширину и минимум 360 логических пикселей по высоте; больший
`custom_minimum_size.y` сцены сохраняется. Размещайте игровые элементы относительно
размера корневого `Control`, используйте якоря и при необходимости задайте большую
минимальную высоту. Не предполагайте, что размер сцены совпадает с размером окна:
на небольшом экране пользователь сможет прокрутить содержимое. Проверяйте ввод и
визуальную компоновку готовых игр в составе приложения.

## Поток

1. Перед запуском сохраните опрос через экран приложения и зафиксируйте копию
   `profile_id` и `survey` именно для этой проверки. Если пользователь отменил
   задание или переключил профиль, не создавайте полную сессию.
2. Игра реакции возвращает исходные попытки, игра памяти — число верных и общее
   число попыток. Обе игры должны явно подтвердить согласованную версию протокола.
3. После получения обоих сигналов приложение само сохраняет результаты в очередь.
   Для альтернативного адаптера доступен метод на корневой сцене приложения:

```gdscript
var outcome: Dictionary = app.accept_game_results(profile_id, survey, reaction, memory)
if outcome.ok:
    # Сессия находится в локальной очереди. Покажите кнопку отправки или
    # вызовите app.send_pending() для текущего выбранного профиля.
    pass
else:
    # Результат не был поставлен в очередь. Сохраните его в игре и покажите
    # понятную ошибку; не генерируйте данные и не сообщайте об успехе.
    print("Не удалось подготовить сессию: ", outcome.error)
```

Пример формата (числа ниже только для тестов, не используйте как реальные данные):

```gdscript
var survey = {"sleep_hours": 8.0, "fatigue": 0.0, "stress": 2.0, "mood": 7.0}
var reaction = {
    "protocol_version": "reaction-memory-v1",
    "trials": [{"outcome": "valid", "reaction_ms": 230},
               {"outcome": "premature"}, {"outcome": "missed"}]
}
var memory = {"protocol_version": "reaction-memory-v1", "correct": 3, "total": 4}
```

`valid` требует `reaction_ms` 1–10000; `premature` и `missed` не содержат
`reaction_ms`. Нужны 1–200 попыток реакции и 1–1000 попыток памяти; число
верных ответов — целое от 0 до общего числа. Опрос принимает сон 0–24 часа,
остальные показатели 0–10. Отсутствующие значения не заменяются нулями.

## Очередь и повторная отправка

Клиент записывает полную сессию с UUID и UTC-временем в отдельный файл в
`user://pending_sessions` до отправки. После завершения обеих игр пользователь
может отправить эту проверку и сразу открыть отчёт. Кнопка на экране обзора
отправляет все ожидающие записи выбранного профиля. После подтверждённого ответа сервера
200/201 с соответствующими UUID и профилем файл удаляется. При ошибке запрос
можно повторить без изменения payload или UUID; сервер обрабатывает идентичный
повтор без создания дубликата. При конфликте 409 запись остаётся в очереди
и требуется разбор причины, а не создание нового UUID.

Если приложение не может прочитать папку очереди, проверить файл `.json` или
обнаруживает незавершённый `.json.tmp`, на обзоре появляется предупреждение и
путь к папке. Такие файлы не удаляются и не отправляются автоматически. Можно
отправить проверенные записи выбранного профиля; предупреждение останется, пока
проблемные файлы не будут исследованы. Перед восстановлением сохраните копию всей
папки; не редактируйте UUID и данные уже отправленных сессий.

Данные на диске не зашифрованы. Незавершённая игра не сохраняется; проверка с
реальными сценами команды и сервером ещё необходима.
